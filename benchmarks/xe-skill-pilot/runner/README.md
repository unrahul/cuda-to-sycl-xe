# Codex offline pilot runner (blocked pending isolation verification)

`pilot.py` is a prototype controller, currently **locked against launching evaluation models**. `--probe-only` checks a command sandbox. It is not yet evidence that all model-visible tools and skill catalogs satisfy the experiment boundary. Do not use the 24-task evaluation until those gaps are closed.

Intended controller interface:

```sh
./pilot.py --workdir /tmp/DEDICATED_WORKDIR --prompt /path/to/prompt.txt \
  --result /path/outside/workdir/new-results --model gpt-6.1-sol --effort high --probe-only
```

The work directory must contain only the selected task, the chosen frozen skill and curated reference bundle if applicable, and its writable output. The caller must stage these before launch. The runner creates a separate temporary `CODEX_HOME`, copies only existing file-backed authentication into it with mode 0600, uses a minimal process environment, and removes the temporary home after exit. Nothing from authentication is intentionally written to results. Results can contain task output and are private. `--probe-only` makes no model request.

The profile allows `:minimal`, this installation's exact Codex executable, `/opt/intel/oneapi/compiler/2025.3/{bin,lib,include}` (installed compiler SDK), and the task workspace. It disables command network access. Web search, apps, plugins, hooks, browser use, computer use, memories, multi-agent, and skill MCP dependency installation are disabled in the prototype config. The configuration also sets `skip_host_skill_discovery`; its effect on both automatic system skills and the intentionally supplied skill has not been established. No MCP servers are configured in the clean home. The profile is a command sandbox; model/auth transport is separate. See [official permissions documentation](https://learn.chatgpt.com/docs/permissions) and [boundary guidance](https://learn.chatgpt.com/docs/cyber-safety/recommended-configuration#define-and-enforce-approved-boundaries).

The compiler SDK directories are readable as dependencies; their contents need an audit before treating them as public-only. The wrapper checks one existing repository directory and a separate sentinel, rather than enumerating every private path. It does not yet prove the behavior of built-in file tools, model-visible web tools, skill discovery, or the evaluator interface. Its probe also does not verify the actual task's compiler invocation. The task workdir should not contain untrusted symlinks to external files. The probe must run again on the real machine and task workspace for each run; a fail means no model launch.

## Recorded evidence

`model-preflight.jsonl` is the complete event stream for one authorized tiny CLI model request. It used `/home/rahul/.local/bin/codex` 0.167.0, a fresh temporary HOME and CODEX_HOME with copied existing file authentication, and:

```sh
codex exec --ephemeral --skip-git-repo-check --ignore-rules -C /tmp/xe-probe.kMHPE5/work -m gpt-6.1-sol -c 'model_reasoning_effort="high"' --json 'Reply with exactly PILOT_OK. Do not run tools.'
```

It exited 0 and returned `PILOT_OK`, demonstrating authentication and provider transport. The event stream does not attest to the provider-returned model or effort; those were requested settings. The sandbox config for this request was the basic minimal workspace profile, not the later full set of feature disables in the prototype. No GPU was used.

`sandbox-probe.json` records a later probe of the prototype profile, without a model call: workspace write succeeded; reads of a separate control file, copied auth file, and the project directory failed; TCP and Docker Unix socket connections failed. `/var/run/docker.sock` existed at probe time. The executable and profile commands are recorded verbatim in the JSON; temporary paths no longer exist.

**Blocking finding:** Running the CLI with a new clean CODEX_HOME automatically materialized five system skill files (skill-installer, skill-creator, review-agent, openai-docs, imagegen). The later prompt inspection found none of the checked bundled skill names after disabling bundled skills and automatic skill instructions; the frozen skill must be supplied as ordinary task files. A negative shell-read check alone cannot establish the model toolset or skill catalog. Hosted web search and all non-shell tools likewise need an actual negative tool-availability check under the final config. Until then, the runner refuses model launch rather than claiming a strict offline evaluation.

## Follow-up isolation diagnostic

The updated prototype sets `skills.bundled.enabled = false`, `skills.include_instructions = false`, and `features.skip_host_skill_discovery = true`; the frozen skill would be supplied as ordinary task files, not registered as a skill. The SDK grant is now limited to compiler 2025.3's `bin`, `lib`, and `include`. Other Intel SDK directories are excluded. Compiler functionality with this narrowed grant is not yet verified.

A diagnostic model turn under `--strict-config` ran shell checks, all denied as intended; see `diagnostic-shell.jsonl`. A separate diagnostic demonstrated an actual built-in `codex` MCP resource-list call returning an empty list, even though `codex mcp list` reported no configured servers; see `diagnostic-tool-surface.jsonl`. That diagnostic's claim to have called the agent list is not supported by a corresponding tool-call event, so it is not proof of an actual delegation.

More decisively, clean-home `codex debug prompt-input` under the final feature settings shows a `collaboration` tool namespace including `spawn_agent` even with `features.multi_agent = false`. Extracted names are recorded in `prompt-surface.json`; the full debug prompt was not saved because it includes system and environment context. The same output did not contain the names of the bundled skills checked. Whether an advertised delegation tool can actually execute is unproven, but its presence violates the requested fixed tool surface. Thus model launch remains locked. `--diagnostic` is reserved for controller-owned inspection and must never receive benchmark content.

## Claude Bash-only fallback

`claude_pilot.py` runs Claude Code 2.1.319 with `--model claude-opus-5-5 --effort high`, `--tools Bash`, safe mode, disabled slash commands, strict empty MCP, no Chrome, and a clean temporary home with only file-backed OAuth authentication copied. The driver can contact Anthropic; documented `CLAUDE_CODE_SHELL_PREFIX` routes each Bash tool command through the separate offline Codex permission sandbox. It does not grant the host's incompatible 2025 SDK. The caller must stage only the selected task, optional frozen skill and curated reference packet, and optional public 2026 SDK header closure, then mark those paths with repeated `--read-only` flags. Per-run probes check each marked path refuses writes. Controller, source repository, auth, and sibling runs remain outside the workspace.

The controller supplies `--task-id`, `--workdir`, `--prompt`, `--result`, `--controller`, and `--run-dir`. Inside the workdir the candidate must be `submission/model_new.py`. To request up to six assessments, the agent writes `requests/N.json` containing exactly `{"id": N}` for N from 1 to 6 and reads `feedback/N.json`. The host fixes task, candidate, evaluator command, and trusted output directory; the agent cannot supply command arguments or paths. Feedback is restricted to task/status/correctness/backend/timings/speedup and error categories; candidate-load and candidate-policy messages are permitted only after the trusted controller has scrubbed them. Submission traversal is anchored to a pre-opened directory FD; symlinks and non-regular entries are rejected, and bounded source files are snapshotted outside the workdir before the trusted evaluator independently snapshots them. Final evaluation is an external controller action. Duplicate IDs are processed at most once per runner process; the trusted evaluator enforces the persistent limit.

`claude-preflight.jsonl` is a redacted, structurally faithful excerpt of a real one-request diagnostic: server response model `claude-opus-5-5`, only `Bash` callable, no MCP servers, skills or slash commands, and the actual Bash tool's sandboxed repo/auth/network checks failed as expected. It was launched from the repository cwd by mistake; the shell wrapper used an isolated workdir. The production runner launches the driver itself in the isolated task directory and fails on an unexpected init cwd. The init reports three platform-bundled plugin metadata entries and four agent names; neither the Skill nor Agent tool was exposed, and safe mode and disabled slash commands suppress customizations. No claim is made that the platform lacks this internal metadata.

`claude-sandbox-probe.json` records a later no-model per-run probe including a read-only task file. A host-only fake evaluator self-test exercised the mailbox and fixed controller arguments; it is not an end-to-end GPU assessment. The unscored real end-to-end fixture passed: Claude generated an x+1 SYCL candidate, used the mailbox, and assessment 4 returned correct=true on the GPU. See fixture-evidence for raw events and feedback. Scored task staging and campaign control remain the parent controller's responsibility. Shell prefix and sandbox behavior are documented by [Anthropic](https://code.claude.com/docs/en/env-vars) and [OpenAI](https://learn.chatgpt.com/docs/permissions).

The per-model limits are 7200 seconds and 120 completed model response IDs; a 121st started response triggers termination and is reported as a budget hit. Assessments have a 2700-second outer bound covering the controller's 600-second lock wait and 1800-second execution timeout plus cleanup. On controller overrun, the runner terminates its owned process group and removes containers named for that controller PID; cleanup failures are reported as `controller_cleanup_unverified`. After model exit the runner waits for any active assessment to finish before writing status. An isolated no-model fixture verified this drain behavior.

After the first scored-protocol qualification exposed generic-only feedback for lazy extension compilation, that attempt was stopped and excluded. The runner now permits the trusted controller's sanitized `candidate_build` message up to 6,000 characters; existing `candidate_load` and `candidate_policy` limits remain 3,000. The controller owns compiler-only classification and sanitization. The replacement campaign uses fresh contexts and the same frozen draw.
